# Faza F1: walking skeleton

Stan na 2026-11-02. Cel fazy: paczka `.qpkg`, która instaluje się na prawdziwym NAS-ie, startuje
sama po restarcie, ma wpis crona i daje się czysto odinstalować, zanim powstanie logika pomiarów.
Fazę zamyka bramka **G1** na TS-464 (lista kontrolna niżej).

## Co jest w paczce 0.1.0

| Element | Stan w F1 |
|---|---|
| `qnetspeed version` | wersje qnetspeed, librespeed-cli i iperf3 (z tego samego `bin/`) |
| `qnetspeed config show / check / get / set` | pełna lista kluczy ze spec pkt 10, walidacja, zapis atomowy; `set` wymaga restartu usługi |
| `qnetspeed daemon` | strona statusu na `WEB_PORT` (8888) i `GET /api/v1/status`; nagłówki bezpieczeństwa z pkt 14.2 |
| `qnetspeed cron` | bierze blokadę testu (czeka do 15 min) i zapisuje w `data/qnetspeed.log` linię `cron: run`; testy z harmonogramu przyjdą w F3 |
| blokada testu (`internal/lock`) | `flock(2)` na `data/.test.lock` z opisem trwającego testu, kod 75 przy zajętej |
| `qnetspeed.sh` | start / stop / restart / status / enable / disable / remove wg pkt 8.2 |
| `package_routines` | sprzątanie crona i dowiązania po odinstalowaniu (pkt 8.3) |
| `librespeed-cli`, `iperf3` | dołączone, jeszcze nieużywane przez `qnetspeed` |

## Skąd wziąć paczkę

Każdy push i PR buduje workflow **build** w GitHub Actions. W przebiegu otwórz zakładkę
**Summary**, sekcja **Artifacts**, i pobierz `qnap-netspeed-qpkg` (zip). W środku:

- `qnap-netspeed_0.1.0_x86_64.qpkg`: dla TS-464,
- `qnap-netspeed_0.1.0_arm_64.qpkg`: dla NAS-ów z aarch64 (eksperymentalna),
- `SHA256SUMS`.

## Instalacja na TS-464

1. Skopiuj `qnap-netspeed_0.1.0_x86_64.qpkg` do folderu udostępnionego, np. przez SMB do `Public`
   (`/share/Public/`). Nie do `/tmp`.
2. Zaloguj się przez SSH jako `admin` i sprawdź sumę (porównaj z `SHA256SUMS`):

   ```sh
   sha256sum /share/Public/qnap-netspeed_0.1.0_x86_64.qpkg
   ```

3. Zainstaluj:

   ```sh
   sh /share/Public/qnap-netspeed_0.1.0_x86_64.qpkg
   ```

   Na końcu powinno być `[App Center] Installed Net Speed 0.1.0 in …` i `Enabled Net Speed`.
   `qpkg_cli -m` dla paczki niepodpisanej nic nie instaluje (spec pkt 12.1), dlatego `sh`.
   Jeśli instalator odmówi z powodu braku podpisu: App Center → Ustawienia → zezwól na aplikacje
   bez ważnego podpisu cyfrowego, zainstaluj, potem wyłącz z powrotem.
4. Sprawdź: `qnetspeed version` w nowej sesji SSH oraz `http://<adres-NAS>:8888/` w przeglądarce.

Aktualizacja to ten sam krok 3 z nowszym plikiem; odinstalowanie: App Center → Net Speed → Usuń.

## Co sprawdza CI (bez NAS-a)

- `go test` dla `config`, `lock`, `web` i poleceń CLI (w tym `cron` przy zajętej blokadzie).
- `scripts/test-service.sh`: `qnetspeed.sh` w chroot z BusyBox i atrapami `/sbin/getcfg`,
  `/sbin/setcfg`, `/sbin/log_tool`, z prawdziwym binarium i apletem `crontab`: start, idempotencja,
  restart po zmianie portu i harmonogramu, stop, `Enable=FALSE`, zajęty port, błędna konfiguracja,
  demon, który nie wstał, cudzy `/usr/bin/qnetspeed`, odinstalowanie według `package_routines`.
- Job `package`: `qbuild` dla obu architektur, kontrola zawartości (`scripts/check-qpkg.sh`), potem
  **instalacja paczki x86_64 jej własnym instalatorem QDK** (`sh plik.qpkg`) w tym samym chroot,
  aktualizacja z zachowaniem konfiguracji i danych, odinstalowanie przez `.uninstall.sh`.

To nie zastępuje G1: chroot nie ma prawdziwego App Center, crond, restartu ani firmware'u QTS.

## Odstępstwa od specyfikacji i ustalenia

1. **Próg rozmiaru paczki:** spec pkt 11.2 (krok 6) zakłada, że `.qpkg` ma co najmniej 70% sumy
   binariów. Pomiar: binaria Go po gzip mają ok. 41% (x86_64: 28,3 MB binariów → 11,6 MB paczki),
   więc próg 70% odrzucałby każdą poprawną paczkę. Kontrola porównuje rozmiar z sumą binariów
   skompresowanych `gzip -9` (próg 90%); pusta paczka nadal jest wykrywana.
2. **Kolejność w `start`:** sprawdzenie „już działa” jest przed kontrolą portów (spec ma odwrotnie),
   bo działający demon sam zajmuje `WEB_PORT`.
3. **Linia crona** ma ścieżki w cudzysłowach: `[ -x "<QPKG_ROOT>/bin/qnetspeed" ] && "<QPKG_ROOT>/bin/qnetspeed" cron …`.
   `CRON_SCHEDULE` przyjmuje tylko cyfry i `* / , -` (linia trafia do crontaba roota).
4. **`QPKG_VER` = `0.1.0`** do czasu wydania; binaria spoza tagu mają wersję `0.1.0-dev+<commit>`.
   Tag `vX.Y.Z` musi być równy `QPKG_VER` (sprawdza `scripts/package-qpkg.sh`).
5. **`config set` nie przeładowuje demona** (przeładowanie w F4); trzeba zrestartować usługę.
   Log demona `data/qnetspeed.log` nie ma jeszcze rotacji 1 MB × 3 (F4).
6. **QDK z `.deb`:** `qdk.conf` wylicza `QDK_PATH` z bieżącego katalogu, więc `package-qpkg.sh` podaje
   `QDK_SCRIPTS_DIR` i `QDK_TEMPLATE_DIR` jawnie. `qbuild --extract` na GNU/Linux potrafi uciąć
   `data.tar.gz` (`dd bs=1024 count=N` z potoku), dlatego `check-qpkg.sh` rozpakowuje paczkę sam.
7. **Port iperf3 w F1 nie jest sprawdzany przy starcie.** Spec pkt 8.2 krok 6 sprawdza `WEB_PORT`
   i `IPERF_PORT`, ale serwer iperf3 uruchamia demon dopiero od F4. Na TS-464 port 5201 był zajęty
   przez inny program i blokował start paczki, która go nie używa. Kontrola `IPERF_PORT` wraca w F4,
   tylko przy `LAN_SERVER_ENABLE=1`.
10. **Domyślny `IPERF_PORT` = 5288, nie 5201** (decyzja Marcina, 2026-11-02). Na TS-464 port 5201
    trzymał serwer iperf3 uruchomiony ręcznie z konta użytkownika (`29064/iperf3`). Domyślnego portu
    iperf3 nie da się uznać za wolny na cudzych NAS-ach, więc paczka ma własny. Klient iperf3 na
    drugim komputerze musi podać port: `iperf3 -c <NAS> -p 5288` (do README w F6). Aktualizacja
    zachowuje konfigurację, więc istniejąca instalacja ma dalej `IPERF_PORT=5201`, dopóki nie zmieni
    się jej ręcznie (`qnetspeed config set IPERF_PORT 5288`).
11. **W2 (przycisk „Otwórz” przez HTTPS):** sprawdzone na TS-464 z QTS otwartym przez HTTPS: strona
    paczki się nie otwiera, bo `qnetspeed` słucha tylko HTTP na 8888. Zgodnie ze specyfikacją
    (decyzja Marcina, 2026-11-02) nasłuch HTTPS przychodzi w 1.1. W 1.0.0 README podaje adres
    `http://<adres-NAS>:8888/`.
8. **Właściciel plików w paczce:** `tar` zapisuje uid/gid z maszyny budującej, a instalator QDK
   odtwarza je na NAS-ie. Pierwsza paczka miała uid 1001 z runnera GitHub, który na TS-464 należy do
   zwykłego użytkownika, a ten mógłby podmienić program uruchamiany jako root. `package-qpkg.sh`
   działa teraz jako root i ustawia `0:0`, a `check-qpkg.sh` i test instalacji odrzucają pliki
   innego właściciela i zapisywalne dla grupy lub innych.
9. `qnetspeed` urósł z 1,5 MB do ok. 9 MB (serwer HTTP i szablony z biblioteki standardowej Go).
