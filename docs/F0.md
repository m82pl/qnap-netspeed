## W1: `librespeed-cli --json` v1.0.14 {#w1}

Źródło: kod v1.0.14 (commit `42e5f76c90e64e04ab7079fd76d833dfe41805da`), pliki `report/json.go`,
`speedtest/helper.go`, `defs/bytes_counter.go`, `defs/defs.go`, `output/output.go`.
Potwierdzenie na prawdziwym uruchomieniu: workflow `w1-capture.yml` (CI) oraz TS-464 w F2.
Przykłady: [`testdata/librespeed/v1.0.14/`](../testdata/librespeed/v1.0.14/README.md).

Struktura wyjścia (stdout, jedna linia):

```json
[{"timestamp":"2026-11-02T19:50:00.123456789+01:00",
  "server":{"name":"…","url":"https://…/empty.php"},
  "client":{"ip":"203.0.113.25","hostname":"","city":"","region":"","country":"","loc":"","org":"…","postal":"","timezone":""},
  "bytes_sent":368050176,"bytes_received":1063256064,
  "ping":8.2,"jitter":1.1,"upload":295.1,"download":850.4,"share":""}]
```

Wnioski, które **zmieniają specyfikację** (do uwzględnienia w parserze `wan`, F2):

1. **Jednostki: `download` i `upload` są w Mb/s, nie w bit/s.** Wartość to `bajty/s ÷ 125000`
   (`AvgMbps`), zaokrąglona do 2 miejsc; ta sama liczba, którą tryb tekstowy pokazuje jako „Mbps”.
   Spec pkt 5.1 („bit/s → `/ 1e6`”) jest błędny: parser **nie dzieli** przez 1e6.
   Nie używamy `--bytes` ani `--mebibytes` (zmieniają tylko tryb tekstowy, ale lepiej ich unikać).
2. **Wyjście to tablica** (jeden element na testowany serwer), nie obiekt. Bez `--server` zawsze 0 lub 1 element.
3. **Brak `server.id`** w JSON (tylko `name` i `url`). `server.id` w historii (spec 13.1) wypełniamy
   z `--server`, gdy podany; przy automatycznym wyborze `id` = `null`.
4. **IP klienta jest w `client.ip`, ale nie zawsze.** Pochodzi z `rawIspInfo` backendu; gdy backend go nie
   zwraca jako obiektu, pola `client` są pustymi napisami. Pusty `client.ip` → `public_ip: null`
   i (jak w spec) `same_public_ip` tylko przy `WAN_IP_ECHO_URL`.
5. **Przypadki błędów:**
   - wybrany serwer (`--server ID`) nie odpowiada → **kod 0** i stdout `[]` (komunikat na stderr).
     Parser musi traktować pustą tablicę jako `status: "error"`;
   - żaden serwer z listy nie odpowiada → kod 1, stdout pusty, stderr
     `No server is currently available, please try again later.`;
   - każdy inny błąd (lista serwerów, IP info, ping, download, upload) → kod 1, stdout pusty,
     stderr `Terminated due to error: <przyczyna>`. Błąd pobrania IP info przerywa cały test.
6. Komunikaty postępu idą na stderr, JSON wyłącznie na stdout. Telemetria jest wysyłana tylko przy
   `--share` lub opcjach `--telemetry-*`: nie przekazujemy żadnej z nich.
7. Do budowy trzeba ustawić `defs.ProgName` i `defs.ProgVersion` przez `-ldflags -X`, bo z nich powstaje
   User-Agent (`librespeed-cli/v1.0.14 (linux; amd64)`). Robi to `scripts/build-librespeed-cli.sh`.
8. `--source` i `--interface` wzajemnie się wykluczają (błąd „incompatible options”), zgodnie z `WAN_BIND_MODE`.
9. v1.0.14 wymaga Go ≥ 1.25 (`go.mod`), więc przypinamy Go 1.27.3 dla całego projektu.

- Najnowsze stabilne wydanie: **iperf 3.22** (2026-09-29; zawiera poprawki CVE-2026-101283 i CVE-2026-101276).
- SHA-256 tarballa `iperf-3.22.tar.gz`: `1c0d0fb02c52626111d6e132db80edfbf27bbaff8bd9245df2a371dcb0b35a92`,
  zgodne w dwóch niezależnych ogłoszeniach wydania (GitHub esnet/iperf, dyskusja #2082, oraz lista iperf-dev).
  CI weryfikuje sumę przed budową.
- Budowa w `alpine:3.24.3` (przypięty digest indeksu) natywnie na runnerze danej architektury
  (`ubuntu-24.04` i `ubuntu-24.04-arm`), bez QEMU. Plan A: `--enable-static-bin --disable-shared
  --without-openssl --without-sctp`; gdy binarium nie jest statyczne lub budowa padnie, plan B:
  `LDFLAGS=-static`. Log joba `binaries` pokazuje, który plan zadziałał („W3: plan A OK”).
- Rozstrzygnięcie ostateczne: pierwszy zielony przebieg joba `binaries` (oba plany zawiodły → poprzednie 3.x).
