# Faza F4: demon i API

Stan na 2026-11-03. Cel fazy: demon (`qnetspeed daemon`) nadzoruje `iperf3 -s`, udostępnia REST API
(`/api/v1`) z tokenem administratora oraz punkty końcowe testu z przeglądarki (`/api/st`). GUI (strony)
jest w F5, ale cała logika, którą GUI wywołuje, jest już tutaj i ma testy. Fazę zamyka lista kontrolna
poniżej (scenariusz A8 oraz części A11, A14 i A15; pełne G4 z A9 jest po F5).

## Co jest w paczce 0.4.x

| Polecenie | Co robi | Root? |
|---|---|---|
| `qnetspeed daemon` | serwer WWW + nadzór `iperf3 -s` (uruchamia go skrypt usługi) | tak |
| `qnetspeed lan-server start\|stop\|status [--json]` | steruje serwerem iperf3 przez API demona (`127.0.0.1:WEB_PORT` albo `WEB_BIND`) | `start`/`stop` tak, `status` nie |
| `qnetspeed web-token` | wypisuje token administratora (`data/web.token`) | tak |

### Serwer iperf3 (spec pkt 5.2.1)

- Demon uruchamia `iperf3 -s -p IPERF_PORT --forceflush [-B LAN_BIND]` jako proces potomny (bez `-D`), jego
  wyjście trafia do `data/qnetspeed.log` z prefiksem `iperf3:`.
- Gdy proces padnie, demon uruchamia go znowu po 1 s, 2 s, 4 s … do 60 s. Przebieg dłuższy niż 60 s zeruje
  opóźnienie. Stan i liczba restartów są w `GET /api/v1/status` (`lan_server`).
- Zajęty `IPERF_PORT`: skrypt usługi odmawia startu (`log_tool -t 2` z numerem portu, wyjście 1), jak dla
  `WEB_PORT`. Gdyby port zajęto już po starcie, demon zgłasza stan `port_busy` z komunikatem
  „port … is already in use by another program (IPERF_PORT)”, próbuje ponownie z tym samym opóźnieniem i nie
  uruchamia iperf3, dopóki port nie jest wolny.
- `LAN_SERVER_ENABLE=0`: serwer się nie uruchamia, a skrypt nie sprawdza `IPERF_PORT`. `lan-server start`
  odmawia wtedy (HTTP 409), żeby jedno polecenie nie obchodziło decyzji z konfiguracji.
- `lan-server stop` działa do restartu usługi (stan nie jest zapisywany); na stałe wyłącza `LAN_SERVER_ENABLE=0`.
- Zamknięcie demona (SIGTERM) zatrzymuje iperf3 (SIGTERM, po 5 s SIGKILL). Gdyby demon zginął bez sprzątania
  (`kill -9`, OOM), jądro zabija iperf3 (`PR_SET_PDEATHSIG`), więc nie zostaje sierota trzymająca port.

### REST API (spec pkt 14.3)

Odpowiedzi to JSON; błędy mają postać `{"error":"kod","message":"opis"}`. Zmiany stanu tylko przez `POST`/`PUT`
z nagłówkiem `Authorization: Bearer <token>` (ciasteczka i token w adresie są ignorowane, więc nie ma CSRF).

| Żądanie | Dostęp | Odpowiedź |
|---|---|---|
| `GET /api/v1/status` | odczyt | wersja, `test_running` (kto trzyma blokadę), `lan_server`, `warnings` (otwarte problemy z `state.json`) |
| `GET /api/v1/history?type=wan\|lan\|link&last=100&since=7d&iface=eth0[&format=csv]` | odczyt | `{records, skipped_lines}`; `last` 1–5000; `since` jak w CLI (`90m`, `12h`, `7d`, `2w`) albo RFC 3339 |
| `GET /api/v1/link`, `GET /api/v1/routes[?all=1]` | odczyt | to samo co `qnetspeed link --json` i `routes --json` |
| `POST /api/v1/tests/wan` `{ifaces, server_ids}` | admin | 202 `{test_id, …}` + `Location`; 409, gdy trwa inny test |
| `POST /api/v1/tests/lan` `{target, time, parallel, udp[, bidir, iface, bitrate]}` | admin | jak wyżej; `time` 1–300, `parallel` 1–32, `target` jak w CLI |
| `GET /api/v1/tests/{id}` | odczyt | `state` (`running`/`done`/`error`), `results` (rekordy zapisane w historii, `trigger: "web"`) |
| `POST /api/v1/lan-server` `{action: start\|stop}` | admin | stan serwera iperf3 |
| `GET /api/v1/config`, `PUT /api/v1/config` `{values:{KLUCZ:"wartość"}}` | admin | klucze z wartością, domyślną i `restart_required`; `PUT` jest „wszystko albo nic”, błędy per pole w `fields` (HTTP 422) |
| `GET /api/st/ping`, `GET /api/st/download?mb=N`, `POST /api/st/upload`, `POST /api/st/result` | odczyt | test z przeglądarki (niżej) |

„odczyt” = bez tokenu przy `WEB_PUBLIC_READ=1` (domyślnie), z tokenem przy `0`. Sama strona `/` i `app.css`
są zawsze publiczne (GUI musi się załadować, żeby zapytać o token).

**Token** (pkt 14.2): 32 losowe bajty (base64url) w `data/web.token` (0600, root), tworzony przy pierwszym
starcie; wypisuje go `qnetspeed web-token`. Porównanie w stałym czasie. Po 10 błędnych tokenach w ciągu minuty
adres dostaje 429 (także z poprawnym tokenem, do końca okna); brak tokenu nie liczy się jako próba (tak pyta GUI).
Akcje administracyjne i błędne tokeny trafiają do `qnetspeed.log` z adresem IP (bez tokenu). Wymiana tokenu:
usuń `data/web.token` i zrestartuj usługę.

**Testy przez API** biorą tę samą blokadę (`data/.test.lock`) co CLI i cron, więc nigdy nie ma dwóch naraz;
zajęta blokada to 409 z opisem, kto ją trzyma. Stan testów jest w pamięci demona (ostatnie 20); wyniki zostają
w historii. Zamknięcie demona przerywa trwający test.

### Test z przeglądarki (spec pkt 5.2.3)

- `ping` zwraca 204 bez blokady. `download` strumieniuje N MiB (domyślnie 100, 1–1024) z losowego bufora 4 MiB,
  `upload` czyta i odrzuca ciało (do 1 GiB) i zwraca liczbę bajtów oraz czas po stronie serwera.
- Test z przeglądarki to wiele żądań, więc blokadę trzyma strumień (`lan-browser`) i jeszcze 5 s po
  ostatnim: cron i testy z API nie wcisną się między pobieranie a wysyłanie. Gdy trwa inny test, `download` i
  `upload` dają 409. Dwie przeglądarki naraz nie wykluczają się (to ten sam test z punktu widzenia blokady).
- `result` zapisuje w `lan.jsonl` rekord `LAN_BROWSER` (adres klienta i `User-Agent` dopisuje serwer, UA bez
  znaków sterujących, do 200 bajtów). Limit 30 wyników na minutę z adresu, wartości sprawdzane (liczby
  skończone, w rozsądnym zakresie).

## Decyzje, których spec nie rozstrzygał

1. `lan-server start` przy `LAN_SERVER_ENABLE=0` odmawia (pkt wyżej); `stop` nie jest trwałe.
2. `PUT /config` zmienia plik od razu, ale klucze czytane tylko przy starcie (`WEB_PORT`, `WEB_BIND`,
   `IPERF_PORT`, `LAN_BIND`, `LAN_SERVER_ENABLE`, `CRON_SCHEDULE`) wymagają restartu usługi: odpowiedź je wylicza
   w `restart_required`. Pozostałe (progi, `WEB_PUBLIC_READ`, `WAN_*`, `LAN_*` testów) działają od następnego
   żądania, bo demon sam przeładowuje plik po zmianie.
3. Test przez API kończy się stanem `done`, nawet gdy sam pomiar się nie udał (np. brak serwera LibreSpeed):
   wynik pomiaru (`status: ok|error|skipped`) jest w `results`. Stan `error` oznacza błąd samego uruchomienia.
4. `GET /api/v1/status` jest „odczytem”: przy `WEB_PUBLIC_READ=0` wymaga tokenu (także `lan-server status`
   wysyła token, jeśli może go przeczytać).
5. Rotacja historii w demonie następuje po każdym zapisie, jak w CLI (spec wspomina „najwyżej raz na godzinę”;
   zapis jest rzadki, więc nie dodawano drugiego mechanizmu).

## Lista kontrolna F4 (TS-464, jako root: `sudo -i`)

Potrzebny komputer z `iperf3` (kroki 4 i 9). Na Windows w PowerShellu pisz `curl.exe` zamiast `curl`.
Wyniki wpisz w wątku projektu (✓/✗ i wklejone wyjście przy ✗). `NAS` to adres NAS-a, `PC` adres komputera.

1. **Wersja i start.** Po aktualizacji: `qnetspeed version` → `0.4.0…`; `qnetspeed config get IPERF_PORT` (jeśli
   zostało `5201` ze starej konfiguracji i trzyma go ręcznie uruchomiony iperf3, zakończ go albo ustaw
   `qnetspeed config set IPERF_PORT 5288`); `/etc/init.d/qnetspeed.sh restart`.
2. **Serwer iperf3 pod demonem.** `qnetspeed lan-server status` → `iperf3 server: running (pid …, port 5288)`;
   `netstat -tln | grep 5288` pokazuje nasłuch; `tail -n 5 $(getcfg qnap-netspeed Install_Path -f /etc/config/qpkg.conf)/data/qnetspeed.log`
   ma `iperf3 server: started` i `iperf3: Server listening on 5288`.
3. **A11 dla iperf3: zajęty port.** `/etc/init.d/qnetspeed.sh stop`, potem
   `$(getcfg qnap-netspeed Install_Path -f /etc/config/qpkg.conf)/bin/iperf3 -s -p 5288 -D -I /var/run/iperf3-test.pid`
   i `/etc/init.d/qnetspeed.sh start` → ma się nie uruchomić, a w System Logs ma
   być błąd `Start failed: iperf3 port 5288 (IPERF_PORT) is already in use by another program …`. Zabij ten
   iperf3 (`kill $(cat /var/run/iperf3-test.pid)`) i `/etc/init.d/qnetspeed.sh start` → działa.
4. **A8: `iperf3 -c NAS` z komputera.** Na PC: `iperf3 -c NAS -p 5288 -t 10 -P 4` oraz z `-R`. Oczekuję prędkości
   zbliżonej do łącza (na 1G okolice 940 Mb/s). W trakcie, na NAS-ie: `qnetspeed lan-server status` nadal
   `running`.
5. **Nadzór.** `qnetspeed lan-server status --json` (zapisz `pid`), `kill -9 <pid>`, po 2–3 s znowu
   `status --json`: inny `pid`, `restarts` ≥ 1, a krok 4 nadal działa.
6. **Sterowanie.** `qnetspeed lan-server stop` → `stopped`, `iperf3 -c NAS -p 5288` z PC odmawia połączenia;
   `qnetspeed lan-server status` kończy się kodem 1; `qnetspeed lan-server start` → `running`, test z PC działa.
7. **Zatrzymanie usługi sprząta.** `/etc/init.d/qnetspeed.sh stop` → `netstat -tln | grep -E '5288|8888'` puste i
   brak procesu: `ps | grep '[i]perf3'`. Potem `start`.
8. **Token.** `qnetspeed web-token` wypisuje 43 znaki; `ls -l …/data/web.token` → `-rw-------`. Z PC:
   `curl -i -X POST http://NAS:8888/api/v1/lan-server -d '{"action":"stop"}'` → 401. Z tokenem
   (`T=<token>`): `curl -s -H "Authorization: Bearer $T" http://NAS:8888/api/v1/config | head -c 300` → JSON z kluczami.
   `curl -s http://NAS:8888/api/v1/status` (bez tokenu) → JSON z `lan_server.state: running`.
9. **Test LAN przez API i blokada (część A14).** Na PC: `iperf3 -s -p 5288`. Z PC albo z NAS-a:
   `curl -s -X POST -H "Authorization: Bearer $T" http://NAS:8888/api/v1/tests/lan -d '{"target":"PC","time":10}'`
   → 202 z `test_id`. Od razu `qnetspeed wan` na NAS-ie → `trwa inny test: lan-test od …` (kod 75), a
   `curl -s http://NAS:8888/api/v1/status` pokazuje `test_running`. Po ok. 25 s
   `curl -s http://NAS:8888/api/v1/tests/<test_id>` → `state: done`, `results[0].results` z upload/download;
   `qnetspeed history --type lan --last 1` pokazuje ten wynik z `trigger: web`.
10. **Odczyty.** `curl -s 'http://NAS:8888/api/v1/history?type=wan&last=3'`, `…/api/v1/link`, `…/api/v1/routes`,
    `curl -s 'http://NAS:8888/api/v1/history?type=lan&format=csv'` (nagłówek CSV).
11. **Zapowiedź A9: transfer przez `/api/st`.** Z PC: `curl -o NUL -w "%{speed_download}\n" "http://NAS:8888/api/st/download?mb=500"`
    (Linux/macOS: `-o /dev/null`) → bajty/s (na 1G ok. 110 000 000); upload:
    `curl -s -X POST --data-binary @plik_200MB -H "Content-Type: application/octet-stream" http://NAS:8888/api/st/upload`
    → `{"bytes":…,"seconds":…}`. Zapisz oba wyniki: porównamy z iperf3 z kroku 4.
12. **RAM (część A15).** `grep VmRSS /proc/$(cat /var/run/qnetspeed.pid)/status` → poniżej 30000 kB (przed i po
    krokach 9 i 11).
13. **Zmiana konfiguracji przez API.**
    `curl -s -X PUT -H "Authorization: Bearer $T" http://NAS:8888/api/v1/config -d '{"values":{"MIN_WAN_DL_MBPS":"123"}}'`
    → `saved`, `restart_required: []`; `qnetspeed config get MIN_WAN_DL_MBPS` → 123; błędna wartość
    (`{"values":{"WEB_PORT":"80"}}`) → 422 z `fields`, plik bez zmian. Przywróć `qnetspeed config set MIN_WAN_DL_MBPS 100`.
14. **Nie psuje F1–F3.** `http://NAS:8888/` otwiera stronę, `qnetspeed cron` kończy się kodem 0, a w App Center
    paczka jest włączona.

## Testy w CI

Jednostkowe: nadzorca iperf3 na atrapie (argumenty, wyjście do logu, rosnące opóźnienie 20/40/80 ms,
reset po stabilnym przebiegu, zajęty port, brak pliku, zatrzymanie i kontekst, ponowne uruchomienie po
zatrzymaniu); API na atrapie zaplecza (dostęp: brak tokenu, zły, prefiks, wielkość liter, token w adresie i w
ciasteczku, `WEB_PUBLIC_READ`, blokada po 10 próbach i zwolnienie po minucie, brak liczenia pustego nagłówka,
walidacja parametrów, cykl testu, 409 z właścicielem blokady, konfiguracja, log bez tokenów) oraz test
z przeglądarki (rozmiar i nagłówki, losowość, blokada trzymana między fazami i zwalniana, 409, upload, zapis
wyniku, limity, czyszczenie `User-Agent`); polecenia `lan-server` i `web-token`; zaplecze na atrapach exec
(test LAN i WAN przez API zapisuje historię z `trigger: web`, `PUT /config` bez zmian pliku przy błędzie);
prawdziwy proces `qnetspeed daemon` z atrapą iperf3 (start, token 0600, zamknięcie zabija potomka).
Skrypt usługi pod BusyBox: iperf3 jako potomek demona, kontrola `IPERF_PORT`, brak sierot po `stop`.
Job `integration` (część 4 `scripts/integration-test.sh`): prawdziwy demon z prawdziwym statycznym iperf3,
`iperf3 -c` do serwera paczki (A8 na loopbacku), `kill -9` i powrót serwera, `lan-server`, test LAN przez API
z 409 w trakcie, transfer `/api/st`, historia, konfiguracja, blokada po 10 błędnych tokenach, zamknięcie.
